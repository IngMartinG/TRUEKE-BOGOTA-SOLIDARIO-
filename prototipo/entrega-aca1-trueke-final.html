Trueke Bogotá
Solidario

Una plataforma web para que los ciudadanos de Bogotá intercambien bienes y servicios sin usar dinero, diseñada como un sistema distribuido, con comunicación asíncrona entre servicios, persistencia mixta y despliegue en contenedores.

Contexto

El problema y la propuesta

Definición del problema

En Bogotá, muchos hogares acumulan objetos en buen estado que ya no usan, ropa, libros, electrodomésticos, mientras otros ciudadanos necesitan justamente eso y no tienen cómo pagarlo. No existe un canal confiable, geolocalizado y gratuito para poner en contacto a quien sobra con quien necesita.

Resolver esto con una aplicación web monolítica tradicional no escala: los picos de solicitudes de intercambio en horas pico generarían cuellos de botella severos, la falta de una capa de caché haría lentas las búsquedas de publicaciones por categoría o localidad, y el acoplamiento excesivo entre módulos impediría desplegar mejoras de forma continua y segura en la nube.

Propuesta de solución

Trueke Bogotá Solidario es una plataforma web que permite publicar, buscar e intercambiar bienes por trueke directo, sin intermediación de dinero. La arquitectura se diseña como un sistema desacoplado: un front-end de publicaciones y chat, un back-end que expone la lógica de negocio, comunicación en tiempo real entre usuarios mediante eventos, y una estrategia de datos combinada (relacional + caché) pensada para escalar en la nube.

Foco de evaluación

Los cuatro pilares aplicados a Trueke

01

Arquitectura de información & usabilidad

Navegación de cuatro secciones, Explorar, Publicar, Mensajes, Perfil, pensada mobile-first, con un flujo de publicación de tres pasos (foto, categoría, descripción) para bajar la fricción de un usuario que nunca ha usado la app.

Modelado UML/C4 (Draw.io, Mermaid) Flujo de publicación
02

Comunicación entre aplicaciones (Pub/Sub)

Cuando un usuario crea una Solicitud de intercambio, el back-end publica un evento solicitud.creada. Dos consumidores independientes reaccionan: el servicio de notificaciones (envía el correo) y el hub de chat (actualiza la conversación en tiempo real), sin que ninguno bloquee al otro.

SignalR (WebSockets) Redis Pub/Sub Event Bus
03

Persistencia de datos (SQL / NoSQL)

SQL Server guarda lo transaccional, usuarios, publicaciones, solicitudes, historial de intercambios, donde la integridad relacional importa. Redis se usa como caché de sesión, contador de vistas por publicación y broker de los eventos Pub/Sub.

SQL Server Redis
04

Contenedores & servicios cloud

Entorno local reproducible con Docker Compose (API + SQL Server + Redis), con Kubernetes como estrategia de orquestación para escalar horizontalmente la API en picos de solicitudes. Despliegue en Azure App Service dentro de una red virtual (VNet) propia, con Azure Blob Storage para las fotos de publicaciones y pipeline de CI/CD en GitHub Actions.

Docker Compose Kubernetes Azure VNet

Vista de arquitectura

Nivel 2 — Contenedores (C4)

Diagrama de contenedores (Nivel 2 del modelo C4, completo con los niveles 1–4 documentado en el repositorio del proyecto). El Front-end en Angular consume la API en ASP.NET Core; la API persiste en SQL Server y usa Redis como caché y como canal Pub/Sub para eventos en tiempo real.
